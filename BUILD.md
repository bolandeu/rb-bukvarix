# Как собрать базу bukvarix — лучший известный путь + история проблем

Машина, на которой это всё измерялось: Mac, 16 ГБ RAM, 10 ядер. Источник
данных: `keywords213.tsv` от Bukvarix (региональная база ключевых слов,
Москва), 126 784 040 строк, TSV без заголовка (`phrase\tfreq`), 6.95 ГБ.

## Лучший путь (делать так, не так, как делали в первый раз)

```bash
uv add duckdb typer rich pymorphy3 pymorphy3-dicts-ru numpy
uv tool install --editable .

export BUKVARIX_DB_PATH="/путь/к/bukvarix.duckdb"   # держать вне ~/.local/share, где угодно на диске

bukvarix import-keywords keywords213.tsv   # ~4 мин — импорт + физический дедуп перестановок слов
bukvarix normalize                          # ~7 мин — content_signature (стоп-слова) + lemma_signature (леммы)
bukvarix reindex                            # ~16 мин — индексы на signature/content_signature/lemma_signature
# (план) bukvarix build-fts                 # ~2 мин — FTS-индекс для search_smart, см. "В процессе" ниже
```

**Итого ~27 минут** на полный цикл от сырого TSV до рабочей базы с индексами
(126.8М строк). Каждый шаг **идемпотентен** — можно прервать и перезапустить,
уже посчитанное не пересчитывается (кроме `import-keywords`, который всегда
делает `CREATE OR REPLACE TABLE` с нуля).

**Перед `normalize`/`reindex`/любой пересборкой — обязательно бэкап:**
```bash
cp bukvarix.duckdb bukvarix.duckdb.backup_pre_<шаг>
```
Удалять бэкап только после того, как результат шага проверен реальными
запросами (`bukvarix stats`, `bukvarix freq "тест"`), не просто по коду
выхода команды.

## Реальные тайминги (зафиксировано на 113.7М строк после дедупа)

| Шаг | Время | Комментарий |
|---|---|---|
| `import-keywords` (126.8М → 113.7М после дедупа) | 3:55 | без индексации |
| `normalize` (content_signature + lemma_signature) | 6:46 | после фикса на чанкование, см. ниже |
| `reindex` (все 3 индекса на signature-колонках) | 6:44 + 9:43 = 16:27 | двумя прогонами (signature отдельно, потом остальные два) |
| FTS-индекс (`create_fts_index`) на 3М-сэмпле | 2.49с | экстраполяция на 113.7М — **под 2 минуты** |

## Проблемы, с которыми столкнулись, и как решили

### 1. `CREATE UNIQUE INDEX` на `phrase` зависал на 30+ минут

**Причина:** ART-индекс DuckDB на VARCHAR-колонке из 126.8М строк строится
в основном однопоточно (подтверждено через `sample <pid> 3` — процесс
сидел в `duckdb::Prefix::Append`, реально работал, не завис, просто
медленно).

**Решение:** индекс на `phrase` вообще не нужен — ни один запрос не ищет
по буквальному `phrase`, только по `signature`/`content_signature`/
`lemma_signature`. Убрали индексацию из `import_keywords()` совсем,
вынесли в отдельную опциональную команду `bukvarix reindex`.

### 2. `lemma_signature` через `GROUP BY phrase` + `array_agg` — `OutOfMemoryException` (дважды)

**Причина:** ~113.7М почти полностью уникальных групп — хэш-агрегат
такого размера огромен сам по себе, `PRAGMA preserve_insertion_order =
false` + `SET memory_limit = '10GB'` (то, что рекомендует сама ошибка)
не помогли — упало что при 12.7 ГБ лимите, что при 10 ГБ.

**Пробовали и отклонили:** `list_transform` с коррелированным подзапросом
вместо `JOIN` — DuckDB не поддерживает подзапросы в lambda-выражениях
(`Binder Error: subqueries in lambda expressions are not supported`).
Python UDF (dict-лукап на предзагруженном словаре лемм, без `GROUP BY`) —
памяти хватало, но безнадёжно медленно (5М строк оценивались в 14-19
минут, то есть часы на полный датасет — накладные расходы DuckDB на
вызов Python-функции построчно доминируют даже для тривиального
`dict.get()`).

**Решение:** тот же `JOIN` + `GROUP BY`, что и раньше (он был и быстрым,
и корректным на сэмпле — 5М строк за 56.8с без сэмпла, 4.7М строк
(1/24 таблицы) за 5.4с при работе прямо на полной таблице с `WHERE`),
но **разбитый на 24 чанка** через `WHERE hash(phrase) % 24 = i` — так
ни один `GROUP BY` не держит в памяти больше ~1/24 групп одновременно.
Итог: 6:46 на все 113.7М без сбоев.

### 3. Индекс раздувает файл базы сильнее, чем ожидалось

126.8М строк → 6.95 ГБ исходник → 11.03 ГБ после дедупа → 12.95 ГБ после
`normalize` → 20.13 ГБ после индекса `signature` → **38.7 ГБ** после
индексов `content_signature`+`lemma_signature`. То есть три ART-индекса
добавили суммарно ~26 ГБ поверх 12.95 ГБ данных — это оказалась не
"грязь" от повторных `CREATE OR REPLACE TABLE`, а реальная цена индексов
у DuckDB на таком объёме VARCHAR-данных (проверено: пересборка в чистый
файл через `COPY FROM DATABASE` выросла до похожего размера, не дала
экономии — см. проблему 4).

**Решение:** смирились, диска достаточно (100+ ГБ свободно). Если нужно
сжать — можно скопировать только данные без индексов
(`CREATE TABLE dst.keywords AS SELECT * FROM src.keywords`, ~1 минута)
и НЕ строить все три индекса заново, если не все нужны.

### 4. Пересборка в чистый файл (`COPY FROM DATABASE`) сама зависла на 28+ минут

**Причина:** `COPY FROM DATABASE src TO dst` не копирует индексы байт-в-байт,
а **пересобирает их** через ту же дорогую ART-вставку, что и обычный
`CREATE INDEX` — то есть это не быстрое копирование, а полная переиндексация
"в фоне" одной командой, без видимого прогресса по размеру файла.

**Решение:** разбили на два шага вручную — (1) `CREATE TABLE ... AS
SELECT * FROM src.table` только для данных (без индексов, ~1 минута на
113.7М+4.19М строк), (2) `bukvarix reindex` на новом файле отдельно, с
уже понятным временем (~16 минут). В сумме это НЕ сэкономило место (см.
проблему 3) — пересборку в итоге отменили, оставили оригинальный файл.

### 5. `search_smart` (умный поиск по умолчанию) — `ILIKE '%слово%'` это full-scan, 16-30 секунд на запрос

**Причина:** индекс (ART) ускоряет только точное совпадение и префикс.
`ILIKE` с ведущим `%` физически не может использовать дерево-индекс —
нужен полный скан всех 113.7М строк с посимвольным сравнением на каждой.

**Попробовали:** DuckDB FTS-расширение (`INSTALL fts; PRAGMA
create_fts_index(...)`) — инвертированный индекс на `lemma_signature`.

```python
con.execute("INSTALL fts")
con.execute("LOAD fts")
con.execute("PRAGMA create_fts_index('keywords', 'phrase', 'lemma_signature', stemmer='none', overwrite=1)")
# запрос:
con.execute("""
    SELECT phrase, freq_msk_exact, fts_main_keywords.match_bm25(phrase, ?) AS score
    FROM keywords WHERE score IS NOT NULL ORDER BY score DESC LIMIT ?
""", [query, limit])
```
⚠️ Строить индекс нужно на **read-write** соединении (на read-only падает:
`Cannot execute statement of type "DROP"` — `create_fts_index` создаёt
вспомогательные таблицы).

**Реальные цифры на полных 113.7М строк (не экстраполяция с сэмпла —
она соврала для скорости запроса, см. ниже):**
- Сборка индекса: **4:50** (сэмпл на 3М строк предсказывал 2.49с × 37.9 ≈
  под 2 минуты — сборка масштабируется предсказуемо, экстраполяция почти
  верна).
- Запрос: **4.6-6.4с** — а не 0.07с, как показал 3М-сэмпл. Экстраполяция
  по скорости запроса **обманула**: `match_bm25` в этой версии DuckDB,
  похоже, вычисляется по всем строкам таблицы (просто дешевле на строку,
  чем `ILIKE`), а не только по кандидатам из инвертированного индекса —
  поэтому и на маленьком сэмпле было быстро (мало строк), а не потому что
  индекс сработал как ожидается от полноценного inverted-index lookup.
  **Итог: ~3-5x быстрее ILIKE (16-30с → 4.6-6.4с), не 100x+, как казалось
  по сэмплу.** Урок: маленький тест хорош для проверки корректности и
  времени **сборки**, но не для скорости **запроса** на структурах, где
  масштабирование зависит от размера таблицы, а не только от размера
  индекса.

**Важнее скорости — семантика.** `match_bm25('растаможка авто')` — это
**OR с ранжированием**, не AND: даёт **174 370** совпадений (что угодно с
хотя бы одним словом), а не 1 824, что даёт строгий AND-фильтр (`ILIKE`
на каждое слово, обязательны все). Топ по score выглядит хорошо (там
объективно оба слова — bm25 честно ранжирует), но:
- при полной замене AND→OR `total_count`/`total_freq_sum` считаются
  по всем 174к, а не по релевантным 1.8к — теряют смысл, если их
  показывать как "суммарный спрос по похожим";
- если сохранять эти поля в ответе — либо оставлять AND-фильтр (тогда
  скорость не выигрывает, `ILIKE` для WHERE всё равно нужен), либо
  убирать/помечать их как приблизительные (нерелевантно для строгого
  анализа спроса), либо не считать их в ответе вообще и оставлять на
  усмотрение вызывающего (посчитать самому по `results` из JSON, если
  нужно) — тогда OR+bm25 становится чисто выигрышем по скорости и
  качеству топа, без порчи агрегатов.

**Статус: внедрено, затем откачено (2026-08-31).** Сначала внедрили
FTS/BM25 для обычных запросов, решив что неточность `total_count`/
`total_freq_sum` не критична. Дошли до `-слово`: комбинация `match_bm25`
с `AND lemma_signature NOT ILIKE ...` в одном `WHERE` **сломала план
запроса** — то, что само по себе шло 6-9с, зависло на 5+ минут и пролило
**11 ГБ** на диск во временные файлы (`duckdb_temp_storage_*.tmp`, не
убрались сами после `kill`, пришлось чистить руками). Сделали fallback:
`-слово` не через FTS, а через старый AND/ILIKE — но затем нашли баг
серьёзнее.

**Настоящая причина отката — обычный запрос с частым словом ломается
так же, только тише.** `bukvarix search "авто в растаможка"` (со словом
"в" — обычный предлог) дал **14 667 023** совпадения через BM25 (вместо
1 824 у строгого AND) и **27.8с** — то есть OR-семантика BM25 не просто
"немного шумит" на частых словах, она **взрывается**: любое частое слово
в запросе (предлог, местоимение, да что угодно популярное) превращает
"похожие фразы" в "почти вся база", и при этом ещё и медленнее строгого
AND. Того "качество топа компенсирует OR-шум" (что казалось верным на
примере "растаможка авто" без предлогов) **не работает на реальных
запросах** — предлоги встречаются в запросах постоянно.

**Итог: FTS/BM25 убран из `search_smart()` совсем.** Вернулись на
строгий AND/ILIKE (16-30с+, но всегда корректно — фраза считается
только если содержит **все** слова запроса как леммы). FTS-индекс
остаётся построенным в базе (не мешает, не используется) — если
понадобится вернуться к этой идее, делать это нужно с AND-семантикой с
самого начала (например через пересечение списков документов по каждому
термину отдельно, не через `match_bm25` на весь запрос целиком), не
на доверии к тому, что топ по score "и так будет хорошим".

## Общий урок

Почти каждая проблема была одной и той же по форме: **операция, которая
кажется "просто скопировать/проиндексировать", на самом деле требует
пересобрать структуру данных с нуля** (ART-вставка, GROUP BY-агрегация) —
и это дорого при ~100М+ уникальных строк, независимо от настроек памяти/
потоков. Что помогало не терять время:
1. Тестировать на подвыборке (`USING SAMPLE N ROWS` или `WHERE hash(...) % N = i`)
   и экстраполировать время **до** запуска на полном датасете.
2. Снимать стек зависшего процесса (`sample <pid> 3`) прежде чем решать,
   ждать или прерывать — часто "зависшее" на самом деле честно работает,
   просто медленно.
3. Бэкап перед каждым потенциально долгим/необратимым шагом, удалять
   только после проверки реальными запросами.
