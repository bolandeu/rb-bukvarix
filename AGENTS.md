# bukvarix — для агентов

Локальный аналог Wordstat: частотность ключевых слов по Москве
(113.7М фраз), без сети, без ограничений API. Команда `bukvarix`
доступна глобально в shell. История решений и проблем при сборке базы —
`BUILD.md`. Развёрнутые примеры вывода — `EXAMPLES.md`.

Начиная с 2026-09-17 CLI построен на общей архитектуре генератора
(`cli-architecture-refactor`): структурированные ошибки с кодами выхода,
`--json`-конверт `{"ok": ...}`, `bukvarix doctor`, `--dry-run`/`--confirm`
на деструктивных командах. Детали контракта — ниже; полный справочник
для агента без доступа к файлам — `bukvarix --ai`.

## ⚠️ Правило: бэкап перед рискованными изменениями

Единственная страховка от порчи рабочей БД — ручные копии, **CLI сам не
делает бэкап** (это осознанно оставлено за пределами `--confirm`-гейта —
copy 44 ГБ файла на каждый прогон слишком дорого). Обязательно перед:

- изменением кода поискового движка (`src/bukvarix/core/db.py` и вообще
  любой файл под `src/bukvarix/`) — скопировать файл(ы) целиком
  (`cp db.py db.py.bak_<что_меняем>`) перед правкой;
- любым вызовом `bukvarix db import-keywords|normalize|reindex` (эти
  команды и так требуют `--confirm`, но подтверждение — не замена
  бэкапу) — `cp bukvarix.duckdb bukvarix.duckdb.backup_<шаг>` перед
  запуском.

Удалять копию **только после** проверки результата реальными запросами
(`bukvarix stats`, `bukvarix freq/search` на паре тестовых фраз) — не
просто по коду выхода команды. Живой пример, почему это важно: FTS/BM25
внедряли в `search_smart()` (2026-08-31), решение выглядело рабочим на
тестовых запросах, но сломалось на реальном использовании (запрос с
предлогом "в" дал 14.6 млн "похожих" вместо 1.8к) — пришлось откатывать
код обратно на AND/ILIKE. Бэкап БД перед этим экспериментом спас от
необходимости пересобирать индексы заново; для кода такого бэкапа не
было — переписывали руками по памяти. Больше так не делать.

## Контракт вывода

С флагом `--json` — один JSON-объект в stdout, больше ничего (прогресс/
ошибки — в stderr). Успех: `{"ok": true, ...поля команды}`. Ошибка:
`{"ok": false, "error": {"code", "message", "action"}}`. Без флага — вывод
для человека. **Для программного использования всегда добавляйте
`--json`.**

Коды выхода:

```
0  успех
1  общая ошибка (UNEXPECTED — баг, повторить с --verbose; ABORTED — отказ
   пользователя на confirm; DATABASE_NOT_READY — БД ещё не собрана, см.
   'bukvarix db import-keywords')
2  неверные аргументы
3  требуется auth (в bukvarix сегодня ничем не используется)
4  проект не инициализирован (только для init/status/config — search/
   freq/stats/db в проекте не нуждаются)
6  CLI старее, чем требует .bukvarix/config.toml проекта
```

## Команды

### `bukvarix search QUERY [--limit N] [--json] [--csv path]`

Основная команда, поведение по умолчанию — как у настоящего Wordstat:
одним вызовом получаете и частотность самой фразы (`self`), и список
похожих фраз в глубину (`results`) — порядок слов и словоформы в `QUERY`
не важны (ищет по лемме). Поддерживает `+слово` (потребовать) и `-слово`
(исключить) прямо в обычном запросе, без отдельного режима. Работает
с **одной фразой** — группы-альтернативы `(a|b)` не поддерживаются
(сознательно убраны).

```json
{"ok": true, "query": "растаможка авто", "mode": "default", "elapsed_seconds": 16.27,
 "results": [{"phrase": "калькулятор растаможки авто", "freq_msk_exact": 1631}, ...],
 "self": {"phrase": "растаможка авто", "freq_msk_exact": 466, "matched_via": "exact"},
 "total_count": 1824, "total_freq_sum": 12188}
```

- `self` — `null`, если такой фразы нет в базе вообще, **или если в запросе есть `-слово`** (нет единой "канонической фразы" при исключении).
- `results` — строгий AND по леммам: фраза попадает в список, только если содержит **все** слова запроса (как леммы, порядок не важен). `total_count`/`total_freq_sum` — точная сумма/число по этому же AND-набору.
- **Медленно**: полный скан 113.7М строк без индекса (`ILIKE` не может использовать индекс на подстроке) — **секунды-десятки секунд** (16-30с+ на частых словах), не мс. Для быстрого да/нет по одной фразе — команда `freq` (мс).
- Если БД ещё не собрана — ошибка `DATABASE_NOT_READY` (exit 1), не пустой результат.
- ⚠️ Пробовали ускорить через FTS/BM25 (OR-семантика, ранжирование) — **откачено**: на запросах с частыми словами (предлоги и т.п.) OR давал миллионы "похожих" вместо тысяч и был ещё медленнее. Подробности и почему не работает — `BUILD.md`, проблема 5.

**`--mode`** переключает на "инженерные примитивы" — узкие, буквальные,
без лемм, для отладки/точных случаев:

| mode | что делает |
|---|---|
| `contains` | буквальная подстрока, слова подряд в этом порядке |
| `words` | все слова запроса есть во фразе, порядок/соседство не важны, строгий AND (без лемм) |
| `prefix` | фраза начинается с `QUERY` |
| `exact` | только каноническая фраза (после дедупа перестановок), 0 или 1 результат |
| `query` | буквальные операторы `+слово`/`-слово` (без лемм) |

`--csv path.csv` — сохраняет `results` в CSV вместо печати; с `--json`
на stdout идёт подтверждение `{"ok": true, "saved_to": ..., "rows": N}`.

### `bukvarix freq QUERY [--json]`

Только частотность одной канонической фразы, без списка похожих —
то же самое, что `self` из `search`, но быстрее (индексный лукап,
единицы-десятки мс, без скана). Три уровня фолбэка (точное совпадение →
без стоп-слов → через леммы), `matched_via` показывает, какой сработал.
`result: null` — фразы нет вообще, не ошибка. Как и `search`, требует
собранной БД (`DATABASE_NOT_READY`, если её ещё нет).

### `bukvarix stats [--json]`

Путь к БД, размер в байтах, список таблиц, число строк `keywords`.
Работает, даже если БД ещё не существует (`keywords_rows: 0`).

### `bukvarix db ...` — обслуживание базы (не для обычного использования агентом)

`db import-keywords <path.tsv>`, `db normalize`, `db reindex` — разовые
шаги подготовки данных, не часть обычного querying-флоу (см. `BUILD.md`).
Все три **деструктивны** и требуют либо интерактивного подтверждения,
либо явного `--confirm` (под `--non-interactive` без `--confirm` —
отказ с `INVALID_ARGUMENTS`, а не тихое выполнение). Перед реальным
запуском — `--dry-run` для превью, затем ручной бэкап (см. выше), и
только потом `--confirm`.

`db set-path PATH` — сохраняет путь к `.duckdb` файлу для всех остальных
команд (переопределяется переменной окружения `BUKVARIX_DB_PATH` на
время одного процесса/сессии).

### `bukvarix doctor [--json]`

Проверяет: путь к БД и её готовность (`db_path`/`db_ready`), наличие
`.bukvarix/config.toml`-проекта (информационно — не требуется для
search/freq/stats/db), совместимость версии CLI, доступность credential
store. Всегда завершается с exit 0 — сам отчёт и есть результат,
`healthy` говорит, прошли ли все значимые проверки.

## Ограничения

- Только регион Москва, только частотность (без поисковой выдачи/доменов — SERP вне скоупа).
- Нет операторов `"кавычки"`, `!точная форма`, `(a|b)` группы — сознательно не реализованы, работа с одной фразой.
- `search` без `--mode exact`/`freq` — медленный (секунды-десятки секунд), полный скан без индекса. Известная, принятая цена за точность (AND, не OR) — см. `BUILD.md`.
- Данные статичны (дамп от Bukvarix), не обновляются в реальном времени.
- `auth`/credentials существуют в CLI ради единообразия с остальными инструментами автора, но ничем в bukvarix не используются — внешних API нет.
