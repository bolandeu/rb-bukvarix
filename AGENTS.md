# bukvarix — для агентов

Локальный аналог Wordstat: частотность ключевых слов по Москве
(113.7М фраз), без сети, без ограничений API. Команда `bukvarix`
доступна глобально в shell. История решений и проблем при сборке базы —
`docs/build.md`. Развёрнутые примеры вывода — `docs/examples.md`.

Начиная с 2026-09-17 CLI построен на общей архитектуре генератора
(`cli-architecture-refactor`): структурированные ошибки с кодами выхода,
`--json`-конверт `{"ok": ...}`, `bukvarix doctor`, `--dry-run`/`--confirm`
на деструктивных командах. Детали контракта — ниже; полный справочник
для агента без доступа к файлам — `bukvarix --ai`.

## ⚠️ Правило: бэкап перед рискованными изменениями

Единственная страховка от порчи рабочей БД — ручные копии, **CLI сам не
делает бэкап** (это осознанно оставлено за пределами `--confirm`-гейта —
copy 41 ГБ файла на каждый прогон слишком дорого). Обязательно перед:

- изменением кода поискового движка (`src/bukvarix/core/db.py` и вообще
  любой файл под `src/bukvarix/`) — скопировать файл(ы) целиком
  (`cp db.py db.py.bak_<что_меняем>`) перед правкой;
- любым вызовом `bukvarix db import-keywords|normalize|reindex` (эти
  команды и так требуют `--confirm`, но подтверждение — не замена
  бэкапу) — `cp bukvarix.duckdb bukvarix.duckdb.backup_<шаг>` перед
  запуском.

**Куда класть бэкап базы:** только на внешний диск,
`/Volumes/Data/bukvarix/` (на системном диске места под вторую копию
41 ГБ нет). Перед копированием проверить, что диск смонтирован:

```bash
test -d /Volumes/Data/bukvarix || echo "диск не смонтирован"
cp bukvarix.duckdb /Volumes/Data/bukvarix/bukvarix.duckdb.backup_<шаг>
```

Если `/Volumes/Data` не виден — **остановиться и попросить пользователя
подключить диск**, не класть копию в другое место и не пропускать бэкап.

**Изменения кода — в отдельной ветке.** Любая правка движка или сборки
базы делается в ветке `feature/<что-меняем>`, а не в `main`: команда
`bukvarix` установлена глобально как editable-пакет из этого каталога, и
незавершённая правка в `main` тут же ломает инструмент для всех, кто им
пользуется прямо сейчас. Проверить, что установка действительно editable:
в `~/.local/share/uv/tools/rb-bukvarix/uv-receipt.toml` должно быть
`editable = "..."`, а не `directory = "..."` (иначе глобальная команда — застывшая
копия старого кода); переустановка — `uv tool install --editable . --force`.
Дистрибутив называется `rb-bukvarix` (стандарт §10), команда и импорт —
по-прежнему `bukvarix`; установка под старым именем снимается один раз:
`uv tool uninstall bukvarix`, иначе два инструмента делят одну команду.
Проверять изменения — глобальной `bukvarix` из другого каталога, а не
только через `.venv` проекта. В `main` вливать только после шага «проверка
реальными запросами».

Удалять копию **только после** проверки результата реальными запросами
(`bukvarix stats`, `bukvarix freq/search` на паре тестовых фраз) — не
просто по коду выхода команды. Живой пример, почему это важно: FTS/BM25
внедряли в `search_smart()` (2026-08-31), решение выглядело рабочим на
тестовых запросах, но сломалось на реальном использовании (запрос с
предлогом "в" дал 14.6 млн "похожих" вместо 1.8к) — пришлось откатывать
код обратно на AND/ILIKE. Бэкап БД перед этим экспериментом спас от
необходимости пересобирать индексы заново; для кода такого бэкапа не
было — переписывали руками по памяти. Больше так не делать.

## Документация: фиксировать и удачные, и неудачные решения

Карта документов:

| Файл | Что там |
|---|---|
| `docs/build.md` | как собрать базу + история решений: что пробовали, что сработало, что нет и почему |
| `docs/backlog.md` | запланированные задачи с инструкцией для исполнителя |
| `CHANGELOG.md` | изменения по версиям — собирается из `changelog.d/` при релизе, руками не править |
| `docs/examples.md` | развёрнутые примеры вывода команд |

Правило: любой эксперимент с движком поиска или сборкой базы — удачный
или откаченный — записывается в `docs/build.md` сразу по итогам, с
реальными цифрами (время, размер файла, число совпадений), причиной
решения и тем, что именно не сработало. Откаченный эксперимент важнее
удачного: без записи его повторят (см. историю FTS/BM25 — проблема 5).
Готовая задача из `docs/backlog.md` переносится в `docs/build.md` и во
фрагмент `changelog.d/` (см. «Разработка и релиз»), а не удаляется молча.

## Контракт вывода

С флагом `--json` — один JSON-объект в stdout, больше ничего (прогресс/
ошибки — в stderr). Успех: `{"ok": true, ...поля команды}`. Ошибка:
`{"ok": false, "error": {"code", "message", "action"}}`. Без флага — вывод
для человека. **Для программного использования всегда добавляйте
`--json`.**

Коды выхода:

```
0  успех
1  общая ошибка (UNEXPECTED — баг, повторить с --verbose; ABORTED — отказ
   пользователя на confirm; DATABASE_NOT_READY — БД ещё не собрана, см.
   'bukvarix db import-keywords')
2  неверные аргументы
3  credentials неисправны (в bukvarix не бывает: секретов нет)
4  проект не инициализирован (только для init/status/config — search/
   freq/stats/db в проекте не нуждаются)
6  CLI старее, чем требует .bukvarix/config.toml проекта
```

## Команды

### `bukvarix search QUERY [--limit N] [--json] [--csv path]`

Основная команда, поведение по умолчанию — как у настоящего Wordstat:
одним вызовом получаете и частотность самой фразы (`self`), и список
похожих фраз в глубину (`results`) — порядок слов и словоформы в `QUERY`
не важны (ищет по лемме). Поддерживает `+слово` (потребовать) и `-слово`
(исключить) прямо в обычном запросе, без отдельного режима. Стоп-слова
(предлоги, союзы, частицы: «в», «для», «как»…) без `+` игнорируются, как в
Wordstat: «авто в растаможка» = «растаможка авто»; `+в` делает предлог
обязательным. Работает
с **одной фразой** — группы-альтернативы `(a|b)` не поддерживаются
(сознательно убраны).

```json
{"ok": true, "query": "растаможка авто", "mode": "default", "elapsed_seconds": 0.087,
 "results": [{"phrase": "калькулятор растаможки авто", "freq_msk_exact": 1631}, ...],
 "self": {"phrase": "растаможка авто", "freq_msk_exact": 466, "matched_via": "exact"},
 "total_count": 1550, "total_freq_sum": 11387, "engine": "postings"}
```

- `self` — `null`, если такой фразы нет в базе вообще, **или если в запросе есть `-слово`** (нет единой "канонической фразы" при исключении).
- `results` — строгий AND по леммам: фраза попадает в список, только если содержит **все** слова запроса (как **целые** леммы, порядок не важен; «авто» не находит «автомобиль»). `total_count`/`total_freq_sum` — точная сумма/число по этому же AND-набору.
- `engine` — каким путём посчитано: `postings` (инвертированный индекс лемм, **0.1-0.4 с**) или `scan` (полный скан 113.7М строк, **16-35 с**). `scan` бывает, если постингов нет или они устарели (после `db import-keywords`/`db normalize` — тогда в stderr предупреждение; лечится `bukvarix db build-postings`), или по запросу `--mode scan`. `scan` ищет по **подстроке** и поэтому находит больше (`%авто%` → «автомобиль»): числа двух движков на одном запросе могут расходиться — это ожидаемо, подробности в `docs/build.md`, проблема 6.
- Если БД ещё не собрана — ошибка `DATABASE_NOT_READY` (exit 1), не пустой результат.
- ⚠️ До постингов пробовали ускорить через FTS/BM25 (OR-семантика, ранжирование) — **откачено**: на запросах с частыми словами (предлоги и т.п.) OR давал миллионы "похожих" вместо тысяч и был ещё медленнее. Подробности — `docs/build.md`, проблема 5; что сработало вместо него — проблема 6.

**`--mode`** переключает на "инженерные примитивы" — узкие, буквальные,
без лемм, для отладки/точных случаев:

| mode | что делает |
|---|---|
| `contains` | буквальная подстрока, слова подряд в этом порядке |
| `words` | все слова запроса есть во фразе, порядок/соседство не важны, строгий AND (без лемм) |
| `prefix` | фраза начинается с `QUERY` |
| `exact` | только каноническая фраза (после дедупа перестановок), 0 или 1 результат |
| `query` | буквальные операторы `+слово`/`-слово` (без лемм) |
| `scan` | то же, что дефолт, но полным сканом по подстроке (старый движок, 16-35 с) — для сверки с `postings` |

`--csv path.csv` — сохраняет `results` в CSV вместо печати; с `--json`
на stdout идёт подтверждение `{"ok": true, "saved_to": ..., "rows": N}`.

### `bukvarix freq QUERY [--json]`

Только частотность одной канонической фразы, без списка похожих —
то же самое, что `self` из `search`, но быстрее (индексный лукап,
единицы-десятки мс, без скана). Три уровня фолбэка (точное совпадение →
без стоп-слов → через леммы), `matched_via` показывает, какой сработал.
`result: null` — фразы нет вообще, не ошибка. Как и `search`, требует
собранной БД (`DATABASE_NOT_READY`, если её ещё нет).

### `bukvarix stats [--json]`

Путь к БД, размер в байтах, список таблиц, число строк `keywords`.
Работает, даже если БД ещё не существует (`keywords_rows: 0`).

### `bukvarix db ...` — обслуживание базы (не для обычного использования агентом)

`db import-keywords <path.tsv>`, `db normalize`, `db reindex`,
`db build-postings [--temp-dir DIR]` — разовые шаги подготовки данных, не
часть обычного querying-флоу (см. `docs/build.md`). `build-postings`
строит индекс лемм для быстрого `search` (~4.5 мин, +1.5 ГБ к файлу;
промежуточные файлы ~5-10 ГБ — в `--temp-dir`, на этой машине
`/Volumes/Data/bukvarix/tmp`); его надо повторять после
`import-keywords`/`normalize`, они сбрасывают постинги.
Все четыре **деструктивны** и требуют либо интерактивного подтверждения,
либо явного `--confirm` (под `--non-interactive` без `--confirm` —
отказ с `INVALID_ARGUMENTS`, а не тихое выполнение). `--non-interactive` —
глобальный флаг, ставится **перед** командой: `bukvarix --non-interactive
db reindex --confirm`; после команды — ошибка `No such option`. Перед реальным
запуском — `--dry-run` для превью, затем ручной бэкап (см. выше), и
только потом `--confirm`.

`db set-path PATH` — сохраняет путь к `.duckdb` файлу для всех остальных
команд (переопределяется переменной окружения `BUKVARIX_DB_PATH` на
время одного процесса/сессии).

### `bukvarix doctor [--json]`

Четыре проверки: `python`, `cli_version` (установленная версия),
`db_path` (куда смотрит CLI) и `db_ready` (файл БД существует; если нет —
в `detail` подсказка про `db import-keywords`). Проект и credentials не
проверяются — bukvarix ими не пользуется. Всегда завершается с exit 0 —
сам отчёт и есть результат, `healthy` = все проверки `ok`.

## Ограничения

- Только регион Москва, только частотность (без поисковой выдачи/доменов — SERP вне скоупа).
- Нет операторов `"кавычки"`, `!точная форма`, `(a|b)` группы — сознательно не реализованы, работа с одной фразой.
- `search` быстрый (0.1-0.4 с) только при собранных постингах (`engine: postings`); без них — полный скан, 16-35 с. См. `docs/build.md`, проблема 6.
- Данные статичны (дамп от Bukvarix), не обновляются в реальном времени.
- Секретов нет: `bukvarix auth status --json` (общий контракт всех инструментов) отдаёт пустой `credentials` и exit 0; `auth login/logout` нет.

## Разработка и релиз

Общий стандарт — `~/Projects/tools/docs/standard-release.md`, шаблон —
`gh:bolandeu/cli-generator` (обновление: `uvx copier update --trust --defaults`).

```bash
uv sync                             # пишет uv.lock — коммитится
uv run scripts/release.py --check   # весь гейт — перед каждым коммитом
```

- **Гейт перед каждым коммитом** — `uv run scripts/release.py --check`:
  `uv lock --check`, ruff check + format, ty, pytest (порог покрытия,
  контракт и снапшоты `--help`, форма `auth status`), фрагмент changelog,
  сборка wheel с установкой во временный venv (`bukvarix --version` =
  версии wheel). Тесты не трогают реальную базу — autouse-фикстура в
  `tests/test_cli.py` подставляет пустой `BUKVARIX_DB_PATH`.
- **Версия = git-тег** `vX.Y.Z` (uv-dynamic-versioning), `version =` в
  `pyproject.toml` нет и не добавлять. Без тега в истории сборка — `0.0.0`.
- **Changelog = фрагменты.** `CHANGELOG.md` не править; каждое видимое
  изменение — `uv run towncrier create +<slug>.<type>.md -c "..."`
  (added/changed/deprecated/removed/fixed/security, в slug без точек).
- **Релиз** — только с чистого актуального `main`:
  `uv run scripts/release.py patch|minor|major` (гейт, towncrier, коммит
  `Release vX.Y.Z`, тег); push — с подтверждением пользователя. На `0.x`:
  исправление/совместимая фича — patch, ломающее изменение — minor.
- **Справка = докстринги.** Поменял поведение команды — поправь её
  докстринг в том же коммите: одна строка, абзац, строка
  `Example: {cli} <команда> …`; у каждого параметра `help=`. Затем
  `uv run pytest --snapshot-update` и прочитать diff в
  `tests/snapshots/help/`. Следят хуки Claude Code (`.claude/settings.json`),
  git pre-commit (`.githooks/`, `scripts/install_hooks.sh` один раз на клон)
  и `tests/test_help.py`.
- `src/bukvarix/data/SKILL.md` — только конвенции, без списка команд.
